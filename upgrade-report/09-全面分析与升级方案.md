# 09 全面分析与升级方案

分析日期：2026-11-10  
当前版本：`1.1.6`（`main` 与 `origin/main` 齐平）  
分析范围：PHP Web/API、共享 JS 解析器、Electron 桌面端、Capacitor Android 端、构建与发布流程

> 本次只做分析与方案，没有修改任何源码、没有提交、没有推送、没有启动服务。  
> 本机没有 PHP/Composer，Docker daemon 未运行，因此 PHP 侧结论来自代码、PHPUnit 缓存记录和既有测试，未重新执行 PHPUnit/Docker build。JS 侧的契约测试与两端前端构建已实际执行。

## 0. 结论摘要

1. **功能面已经比较完整，主要风险不在“缺功能”，而在“同一套能力维护两遍”。** 12 个点播平台 + 4 个直播平台同时存在 PHP（约 3,058 行）与 JS（约 3,415 行）两套解析实现，另有传输、重试、缓存、发现、允许域名等逻辑重复。任何上游平台变动都要改两处、测两套、发两次。
2. **PHP 与 JS 的解析结果契约已经漂移。** JS 侧统一补齐 `platform/media_type/images/music`；PHP 侧直接返回各解析器的原始数组，12 个点播解析器里只有 4 个会输出 `media_type`，单条解析结果没有 `platform`。网页端用 `platformName(url)` 正则兜底，API 使用方则可能拿到字段缺失的结果。
3. **网页版媒体代理的默认域名白名单漏掉了多个已支持平台的 CDN**（小红书、快手、微博、视频号、最右）。网页端所有媒体都走 `index.php?action=media`，因此这些平台会出现“解析成功但播放/下载 403”，这是当前最值得优先验证和修复的用户可见问题。
4. **工程门禁处于半失效状态。** GitHub 仓库没有 `.github/workflows`；唯一的质量流水线是 Gitee Go 配置，与 `AGENTS.md` 的“只推 GitHub”策略冲突。PHPUnit 记录中仍有 1 个失败用例，且 `.phpunit.result.cache` 被 Git 跟踪。
5. **网页端是 122 KB 的单文件 PHP 页面**（1,308 行 CSS + 798 行主脚本，无打包、无 CSP、无模块边界），这是后续 UI/安全/可访问性升级的最大阻力。桌面端与移动端构建目前都能通过。
6. **建议节奏：先用 1–2 天完成“止血版” v1.1.7，再用约 2 周完成契约统一与前端工程化（v1.2/v1.3），最后评估把 JS 解析器收敛为唯一实现（v2.0）。**

## 3. 问题清单（按优先级）

### P0：正确性与发布阻断

#### P0-1 网页版媒体代理白名单漏平台

- 网页端所有媒体地址都经过 `mediaUrl()` → `index.php?action=media`（`public/app.php:1414`），用于视频、封面、头像、图集、下载。
- 代理入口先执行 `MediaProxy::isAllowedUrl()`（`public/index.php:52-72`、`app/Services/MediaProxy.php:362-398`），默认白名单在 `config/app.php:58-61`。
- 默认白名单包含抖音/B站/西瓜/微视/皮皮虾/皮皮搞笑/TikTok/虎牙/斗鱼等，但**不包含**：
  - 小红书：`xhscdn.com`
  - 快手：`kwaicdn.com`、`kwimgs.com`、`yximgs.com`
  - 微博：`weibocdn.com`、`sinaimg.cn`
  - 视频号：`finder.video.qq.com`
  - 最右：`izuiyou.com`（白名单只有 `ippzone.com`）
- 结果：这些平台解析成功后，网页端播放/下载/封面大概率返回 403，但解析接口本身是成功的，用户看到的是“解析完成但视频打不开”。
- 同一份遗漏也存在于 Electron 与 Android 的本地代理白名单。
- **修复**：补齐域名只是止血；根治需要把白名单收敛为单一来源（构建时生成到 PHP/JS/Java），并加“平台 → 媒体域名”契约测试。

#### P0-2 PHP/JS 解析结果契约不一致

- JS 侧：`normalizeResult()` 保证 `title/author/avatar/uid/like/time/cover/url/music/media_type/images/platform`（`packages/parsers/src/index.js:46-71`）。
- PHP 侧：`VideoParser::parse()` 直接返回解析器原始数组（`app/Services/VideoParser.php:83`），没有统一归一化。
- 现状：只有 `DouyinParser`、`PipixiaParser`、`TiktokParser`、`XiaohongshuParser` 输出 `media_type`；单条解析结果没有 `platform`；`images/music` 也不保证存在。
- `public/openapi.yaml` 的 `ParseResult` 却把 `media_type`、`images` 当作正式字段。API 使用方按文档取字段会踩空。
- 网页端只能靠 `platformName(url)` 正则重新推断平台（`public/app.php:1410`），与后端注册表是两套逻辑。
- **修复**：在 PHP 增加与 JS 等价的 `normalizeResult`，补 `platform`、`media_type`、`images`、`music` 默认值；用共享 fixture 做跨语言契约测试；同步 OpenAPI。

#### P0-3 PHPUnit 红灯 + 测试缓存入库

- `.phpunit.result.cache` 记录 `Tests\Unit\DiscoveryBehaviorTest::testSearchRejectsUnsupportedPlatformWithoutNetwork` 状态为 `3`（failure）。
- 该用例仍期望 `Discovery::search('douyin', ...)` 抛 `InvalidArgumentException` 且消息含“抖音”（`tests/Unit/DiscoveryBehaviorTest.php:38-44`），但 v1.1.6 已实现抖音搜索并路由到 `douyinSearch()`（`app/Services/Discovery.php:51-55`），实际会走网络或抛 `RuntimeException`。
- 同时 `.phpunit.result.cache` 被 Git 跟踪，违反 `.gitignore` 意图。
- **修复**：把用例改为“抖音搜索在无签名服务时返回受控错误/或注入假传输层”，并 `git rm --cached .phpunit.result.cache`。

#### P0-4 GitHub 没有 CI，Gitee 流水线与仓库策略冲突

- 仓库没有 `.github/` 目录。
- 唯一流水线 `.workflow/quality-pipeline.yml` 是 Gitee Go 配置，触发器和注释都指向 Gitee。
- `AGENTS.md` 明确要求以后只推 GitHub。
- 结果：当前没有任何自动门禁，PHP 红灯和缓存文件入库都无人拦截。
- **修复**：新增 `.github/workflows/quality.yml`，跑 PHP lint + PHPUnit + smoke + 两个 JS 契约测试 + 两端前端构建；Gitee 配置可保留为历史或删除。

#### P0-5 “跟随系统主题”实际失效 + 深色首屏闪烁

- `applyTheme()` 每次调用都会写入 `localStorage['watermark-parse-theme-v2']`（`public/app.php:2169`）。
- 系统主题监听器只在**该键不存在**时才跟随（`public/app.php:2171-2173`）。
- 首次加载 `applyTheme(preferredTheme())` 已写入键，因此之后系统明暗切换永远不会生效。v1.1.6 更新日志宣称的“主题支持跟随系统明暗切换”与实现不符。
- 页面初始 HTML 没有 `dark` 类，主题脚本在 `</body>` 前才执行，深色用户会先看到浅色闪烁。
- **修复**：`<head>` 内联 3 行脚本先定主题；只在用户手动切换时持久化；系统监听器改为“无手动偏好时跟随”。

#### P0-6 视频失效后的“自动重新解析”被缓存挡住

- 播放失败时网页端会再次调用 `requestParse(currentResult.url)`（`public/app.php:2153-2165`）。
- 但 `/api/v1/parse` 没有 `force` 参数，`VideoParser::parse()` 命中 24h 缓存直接返回旧结果（`app/Services/VideoParser.php:71-76`）。
- 因此“刷新失效媒体地址”实际拿回同一个失效 URL，然后提示“已尝试重新获取”，功能名不副实。
- **修复**：API 增加 `force=1`/`refresh=true`，穿透 `ParseCache`；前端错误重试时带上；批量与单条都要覆盖。

### Phase 3：架构收敛 v2.0.0（10–15 天，建议但需决策）

**推荐方案 A：以 JS 解析器为唯一实现，PHP 通过本地 Node 服务调用。**

- 现有 Docker/`start.sh` 已经为 a_bogus 启动 Node sidecar，部署前提已具备。
- 做法：把 sidecar 扩展为 `/parse`、`/live`、`/discovery` 内部 HTTP 服务；PHP `VideoParser` 改为 HTTP 客户端；用 `PARSER_ENGINE=php|node` 开关灰度。
- 迁移顺序：先切 2 个低风险平台（如 B站、皮皮虾）→ 影子比对 1 周 → 全量切换 → 删除 `app/Parsers/*.php`。
- 收益：平台修复只改一处；删除约 3,000 行 PHP 解析逻辑；跨语言契约测试不再需要。
- 代价：PHP 独立部署必须带 Node（目前抖音已要求）；sidecar 需要进程守护与超时/熔断。

**备选方案 B：保留双实现，但用生成器统一常量 + 跨语言 fixture。**

- 生成平台域名、媒体白名单、UA、画质映射到 PHP/JS/Java；共享 fixture 强制两边输出一致。
- 成本低、风险低，但双倍维护税仍在，适合短期无法接受架构变更时采用。

### Phase 4：持续改进

- 发布自动化：`scripts/release.mjs` 统一升版本（composer/两个 package/Android/OpenAPI）、构建、校验和、创建 GitHub Release。
- 可观测性：结构化 JSON 日志、解析耗时/成功率指标、上游错误码分布；`X-Request-ID` 透传到日志与前端错误提示。
- 缓存：`ParseCache` 单飞/短锁；生产建议 Redis；JS 缓存 LRU。
- i18n：先抽字典，默认 zh-CN，为英文做准备。
- 文档：能力矩阵（平台 × 单条/主页/合集/直播/搜索/评论）、部署矩阵（Docker/裸机/子路径/反向代理）。

## 8. 需要产品决策的 4 件事

1. **解析器是否收敛到 JS（Phase 3 方案 A）？** 推荐“是”，用 `PARSER_ENGINE` 灰度，保留一个版本的 PHP 回退。若短期不具备条件，选方案 B。
2. **B站 DASH 音视频分离如何呈现？** 推荐 API 新增 `audio_url` 并在 UI 标注“视频轨/音频轨”，而不是继续让用户下载无声 MP4。
3. **是否正式支持 iOS？** 目前有 `mobile:add:ios` 脚本但没有 `@capacitor/ios` 依赖；要么补齐依赖与文档，要么删除脚本避免误导。
4. **开启 `API_KEY_ENABLED` 后网页版如何工作？** 目前网页端不会发送 API Key，开启后网页版自身也会 401；需要同源代理注入、前端配置项，或明确“API Key 仅用于外部调用”。
